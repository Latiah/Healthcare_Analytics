 Healthcare Analytics Lab – Star Schema Design Decisions

 Decision 1: Fact Table Grain

choice: One row per encounter.

Reason:
Most of the business queries are based on encounters, so having one row per encounter makes reporting simpler and faster. Diagnosis and procedure details will be stored separately in bridge tables to avoid duplicate rows.



Decision 2: Dimension Tables

 `dim_date`

Stores date information such as:

* Date
* Day
* Month
* Quarter
* Year

 `dim_patient`

Stores patient details:

* Patient ID
* Name
* Gender
* Date of Birth
* MRN
* Age Group

`dim_provider`

Stores provider information:

* Provider ID
* Name
* Credential
* Specialty
* Department

`dim_specialty`

Stores:

* Specialty ID
* Specialty Name
* Specialty Code

 `dim_department`

Stores:

* Department ID
* Department Name
* Floor
* Capacity

`dim_encounter_type`

Stores encounter types:

* Outpatient
* Inpatient
* ER

`dim_diagnosis`

Stores:

* Diagnosis ID
* ICD-10 Code
* Description

`dim_procedure`

Stores:

* Procedure ID
* CPT Code
* Description


Decision 3: Pre-Aggregated Metrics

The fact table will store:

* Diagnosis count
* Procedure count
* Total claim amount
* Total allowed amount
* Length of stay
* 30-day readmission flag

Reason:
These values are calculated once during ETL instead of every time a report is run. This reduces joins and improves query performance.


Decision 4: Bridge Tables

Decision: Use bridge tables.

Bridge tables:

 `bridge_encounter_diagnoses`
 `bridge_encounter_procedures`

Reason:
An encounter can have multiple diagnoses and procedures. Using bridge tables keeps the fact table at one row per encounter while still allowing detailed analysis when needed. It also prevents duplicate rows and improves overall query performance.
